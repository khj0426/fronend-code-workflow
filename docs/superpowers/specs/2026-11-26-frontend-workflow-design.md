# Codex 프론트엔드 워크플로 스킬 설계

## 목적

이 저장소는 여러 프론트엔드 코드베이스에서 재사용할 수 있는 Codex 스킬을 제공한다. 스킬은 Codex가 구현을 시작하기 전에 사용자 의도와 성공 조건을 확인하고, 변경 위험에 맞는 검증을 수행하도록 돕는다.

이 스킬의 목표는 문서의 양을 늘리는 것이 아니다. 요구사항이 불명확한 상태에서 구현하거나, 브라우저 동작을 코드 검사만으로 판단하거나, 요청하지 않은 기능까지 확장하는 일을 줄이는 것이 목표다.

## 범위

첫 버전은 `frontend-workflow` 단일 스킬과 선택형 strict 모드를 제공한다. 다음 작업을 지원한다.

- 기존 프론트엔드 애플리케이션의 기능 추가
- UI 및 상호작용 변경
- 버그 수정과 회귀 방지
- 프레임워크 또는 구조 변경
- 구현 결과 검증과 리뷰
- 수용 기준과 구현·검증 근거의 선택적 추적

첫 버전은 다음 기능을 제공하지 않는다.

- 특정 프레임워크의 프로젝트 생성기
- 별도의 리뷰 또는 회고 에이전트
- CI 설정의 자동 변경
- 사용자가 요청하지 않은 문서, 테스트 또는 외부 서비스 생성

strict 모드는 명시적 요청이나 자동 추천에 대한 사용자 승인으로만 활성화한다. 일반 작업에는 추적 문서를 강제하지 않는다.

`SKILL.md`는 작업 분류, 공통 원칙, 단계 선택만 담는다. 상세 절차는 필요한 단계의 reference만 읽도록 한다.

## 호출 조건

스킬은 사용자가 기존 프론트엔드 코드베이스에서 기능, UI, 동작 또는 구조를 변경해 달라고 요청할 때 적용한다. 단순 설명, 코드 번역, 백엔드 전용 작업, 문서만 작성하는 요청에는 적용하지 않는다.

자동 선택을 허용한다. 사용자는 `$frontend-workflow`로 명시적으로 호출할 수도 있다.

사용자가 프롬프트에 `strict`를 명시하면 strict 모드를 활성화한다. 인증, 권한, 결제, 개인정보, 공용 API, 라우팅·데이터 계약 변경, 단계적 이전처럼 실패 비용이나 영향 범위가 큰 작업에는 Codex가 strict 모드를 자동으로 추천한다. 추천은 활성화가 아니며 사용자 승인 전에는 문서나 추적 파일을 만들지 않는다.

## 작업 분류

스킬은 변경 전에 작업을 세 단계로 분류한다.

### 작은 변경

한정된 스타일, 문구, 정적 콘텐츠처럼 동작과 인터페이스에 영향이 거의 없는 변경이다.

- 의도를 한 문장으로 확인한다.
- 관련 소스와 기존 패턴을 확인한다.
- 필요한 최소 검사와 화면 확인을 수행한다.
- 별도의 설계 문서를 만들지 않는다.

### 일반 기능

상태, 사용자 입력, 네트워크 요청 또는 여러 UI 상태를 포함하는 변경이다.

- 사용자 시나리오와 제외 범위를 확인한다.
- UI 상태와 수용 기준을 제안하고 승인을 받는다.
- 작은 수직 단위로 구현한다.
- 코드 검사와 브라우저 검증을 함께 수행한다.

### 고위험 변경

공용 컴포넌트, 라우팅, 인증, 데이터 계약, 디자인 시스템 또는 프레임워크 구조에 영향을 주는 변경이다.

- 영향 범위와 롤백 방법을 확인한다.
- 대안과 트레이드오프를 제시한다.
- 승인된 설계와 구현 순서를 기록한다.
- 단계마다 회귀 검증을 수행한다.

작업 도중 영향 범위가 커지면 더 높은 단계로 올리고 사용자에게 알린다.

### Strict 모드

Strict 모드는 고위험 변경의 선택적 확장이다.

- `AC-001` 형식의 수용 기준을 작성한다.
- 명세, 계획, 작업 일지, 추적 파일을 기능별 디렉터리에 둔다.
- 모든 수용 기준을 구현 파일과 테스트 또는 수동 검증 근거에 연결한다.
- 외부 패키지가 필요 없는 검사 스크립트로 ID, 상태, 근거, 파일 존재를 확인한다.
- 검사 결과는 테스트 내용이나 구현 품질을 증명하지 않는다고 명시한다.

## 워크플로

### 1. 맥락 조사

Codex는 저장소 지침, 작업 트리 상태, 관련 코드, 테스트, 최근 변경을 먼저 확인한다. 기존 패턴과 사용자 변경을 보존한다. 요청 범위 밖의 리팩터링은 포함하지 않는다.

### 2. 명세

일반 기능과 고위험 변경은 다음 내용을 구현 전에 합의한다.

- 사용자가 하려는 일
- 성공 조건
- 로딩, 성공, 빈 상태, 오류, 권한 없음 등 관련 UI 상태
- 모바일, 키보드, 다크 모드 등 실제로 영향을 받는 환경
- 명시적으로 제외하는 범위

수용 기준은 관찰 가능한 결과로 쓴다. 내부 구현 방법은 기술 결정이 필요한 경우에만 포함한다.

### 3. 구현

구현은 사용자가 확인할 수 있는 작은 수직 단위로 나눈다. 각 단위는 기존 기능을 가능한 한 유지하며 독립적으로 검증할 수 있어야 한다.

Codex는 현재 코드베이스의 도구와 패턴을 우선한다. 새 라이브러리, 외부 서비스, 대규모 구조 변경은 필요성과 비용을 설명하고 승인받은 뒤 적용한다.

### 4. 검증

검증은 변경 위험과 코드베이스의 기능에 맞춰 선택한다.

- 타입 검사와 정적 분석
- 순수 로직 단위 테스트
- 컴포넌트 상호작용 테스트
- 주요 사용자 흐름의 E2E 테스트
- 실제 브라우저에서의 동작, 반응형, 다크 모드 확인
- 키보드 조작, 포커스, 이름과 역할 등 접근성 확인
- 공용 UI의 시각적 회귀 확인

존재하지 않는 검사 도구를 임의로 추가하지 않는다. 수행하지 못한 검증과 이유를 결과에 명시한다.

### 5. 리뷰와 보고

Codex는 최종 변경을 요구사항과 대조한다. 요청 범위 이탈, 회귀 위험, 불필요한 복잡성, 누락된 UI 상태를 확인한다.

최종 보고에는 다음 내용을 간결하게 포함한다.

- 사용자 관점에서 달라진 점
- 변경한 주요 파일
- 수행한 검증과 결과
- 남은 한계 또는 후속 작업

커밋, 푸시, PR 생성, 배포처럼 외부 상태를 바꾸는 작업은 사용자가 요청한 경우에만 수행한다.

## Reference 역할

### `specification.md`

사용자 시나리오, 범위, UI 상태, 수용 기준을 작성하는 방법을 제공한다. 일반 기능과 고위험 변경에서만 읽는다.

### `implementation.md`

수직 단위 분해, 기존 패턴 보존, 상태와 데이터 경계, 변경 중 위험 상승 기준을 제공한다.

### `verification.md`

변경 유형별 테스트와 브라우저 검증 선택 기준을 제공한다. 모든 작업에서 필요한 부분만 읽는다.

### `review.md`

요구사항 대조, 회귀 위험, 접근성, 범위 이탈을 확인하는 최종 리뷰 절차를 제공한다.

### `strict-mode.md`

엄격 모드의 활성화 조건, 산출물, 수용 기준 추적, 검사와 완료 보고 절차를 제공한다.

## 실패 처리

- 요구사항이 불명확하고 합리적 가정이 결과를 크게 바꾸면 구현 전에 질문한다.
- 기존 테스트가 실패하면 이번 변경 때문인지 먼저 구분한다.
- 브라우저 또는 외부 서비스에 접근할 수 없으면 대체 검증을 수행하고 한계를 밝힌다.
- 검증 실패를 숨기거나 성공으로 표현하지 않는다.
- 사용자 변경과 충돌하면 해당 파일을 덮어쓰지 않고 충돌 지점을 보고한다.

## 스킬 자체 검증

첫 버전은 다음 기준으로 검증한다.

- Codex 스킬 구조 검증기가 성공한다.
- `SKILL.md`의 설명만으로 프론트엔드 변경 요청에 선택할 수 있다.
- 작은 변경에는 불필요한 문서를 요구하지 않는다.
- 상태가 있는 기능에는 구현 전 UI 상태와 수용 기준을 확인한다.
- 검증 도구가 없는 저장소에 새 도구를 임의로 설치하지 않는다.
- 커밋과 배포 권한을 기능 구현 권한으로부터 분리한다.
- 고위험 변경에는 strict 모드를 추천하지만 승인 없이 활성화하지 않는다.
- 추적 검사기의 정상·실패·제외·경로 이탈 사례에 대한 자체 테스트가 성공한다.

## 향후 확장 조건

다음 상황이 반복되면 별도 기능을 고려한다.

- 리뷰 관점 분리가 실제 결함을 반복해서 발견하면 `frontend-review` 스킬을 분리한다.
- 작업 일지에서 같은 실수가 반복되면 `frontend-reflect` 스킬을 추가한다.
- 여러 저장소에서 필요성이 확인되면 추적 검사를 CI에 연결하는 선택형 가이드를 추가한다.
- 특정 프레임워크의 검증 절차가 충분히 달라지면 프레임워크별 reference를 추가한다.
