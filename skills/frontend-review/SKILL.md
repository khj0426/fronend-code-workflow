# 프론트엔드 리뷰

코드를 수정하지 않고 최종 diff와 영향받는 사용자 흐름을 독립적으로 검토한다.

## 절차

1. 저장소 지침, 사용자 요청, 최종 diff, 관련 테스트를 확인한다.
2. 저장소에 요구사항, 이슈, PR 설명, 설계 문서 또는 추적 자료가 있으면 실제 변경과 대조한다. 특정 형식을 요구하거나 문서를 새로 만들지 않는다.
3. 다음 영역에서 실제 동작 오류와 회귀를 찾는다.
   - 로딩, 성공, 빈 상태, 오류와 복구 흐름
   - 중복 요청, 오래된 상태, 정리 작업과 경쟁 상태
   - 키보드 조작, 포커스, 접근 가능한 이름과 상태 알림
   - 좁은 화면, 긴 콘텐츠, 테마와 모션 설정
   - 서버와 클라이언트 경계, 하이드레이션, 브라우저 전용 API
   - 공개 props, 라우트, URL, 저장소 키와 데이터 형태
4. 재현 가능하거나 코드로 입증할 수 있는 항목만 finding으로 작성한다.
5. finding을 심각도순으로 보고하고, finding이 없으면 검토 범위와 남은 검증 공백을 밝힌다.

## 심각도

- `P1`: 보안, 데이터 손상, 핵심 흐름 실패처럼 배포를 막아야 하는 문제
- `P2`: 실제 사용자에게 영향을 주는 기능 또는 접근성 회귀
- `P3`: 제한된 조건에서 발생하는 낮은 위험의 문제

확신이 부족한 항목은 finding으로 단정하지 않고 확인이 필요한 가정으로 분리한다.

## Finding 형식

각 finding에는 심각도와 요약, 파일과 가능한 경우 정확한 줄, 문제의 근거, 사용자 또는 시스템에 미치는 영향을 포함한다. 수정 방향은 문제를 이해하는 데 필요할 때만 짧게 덧붙인다.

## 제외

포맷, 단순 취향, 사소한 네이밍, 자동 도구가 이미 잡는 항목, 근거 없는 리팩터링 제안은 보고하지 않는다. 사용자가 수정을 별도로 요청하지 않으면 코드, 커밋, PR을 변경하지 않는다.
