# 명세

일반 기능과 고위험 프론트엔드 변경을 구현하기 전에 이 문서를 읽는다.

## 사용자 결과를 정의한다

주요 시나리오를 관찰 가능한 문장으로 작성한다.

> `<시작 조건>`일 때 사용자는 `<행동>`할 수 있고 `<결과>`를 확인한다.

결과와 구현 방법을 분리한다. “필터가 URL에 반영된다”는 관찰 가능한 결과다. “Zustand를 사용한다”는 기술 결정이다.

## 관련 UI 상태를 고른다

가능한 모든 상태를 형식적으로 나열하지 않는다. 다음 상태를 검토하고 기능이 실제로 진입할 수 있는 상태만 남긴다.

- 초기 또는 대기
- 로딩 또는 처리 중
- 성공
- 빈 결과
- 유효성 검사 실패
- 복구 가능한 오류
- 이용 불가 또는 권한 없음
- 오래된 데이터, 낙관적 업데이트 또는 일부만 갱신된 데이터

각 관련 상태에서 사용자가 무엇을 보고, 어떤 행동을 할 수 있고, 어떻게 다음 상태로 이동하는지 정의한다.

## 영향을 받는 환경을 확인한다

변경에 따라 결과가 달라질 수 있는 환경만 포함한다.

- 좁은 화면과 넓은 화면
- 키보드와 포인터 입력
- 라이트 모드와 다크 모드
- 모션 감소 설정
- 서버 렌더링과 하이드레이션
- 느린 네트워크와 반복 제출
- 로그인 상태와 비로그인 상태

## 수용 기준을 작성한다

수용 기준은 관찰하거나 테스트할 수 있는 결과를 설명해야 한다. 의미 있는 기준을 짧게 작성하고 요구사항 전체를 반복하지 않는다.

좋은 예:

- 유효한 폼을 제출하면 요청은 한 번만 전송되고, 처리 중에는 중복 제출이 비활성화된다.
- 유효성 오류는 해당 입력과 연결되고, 포커스는 첫 번째 오류 입력으로 이동한다.
- 결과 페이지로 돌아오면 URL에 기록된 필터가 복원된다.

피해야 할 예:

- 컴포넌트가 올바르게 동작한다.
- 클린 코드를 사용한다.
- 폼을 위한 훅을 추가한다.

## 범위를 제한한다

분석 이벤트, 기기 간 저장, 애니메이션, 새 디자인 시스템 요소, 이전 라우트 지원처럼 범위가 커지기 쉬운 항목은 제외 여부를 명시한다.

답에 따라 결과가 크게 달라질 때만 한 번에 하나의 질문을 한다. 저장소나 요청에 답이 이미 있으면 다시 묻지 않고 진행한다.
