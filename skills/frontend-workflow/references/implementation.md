# 구현

사용자 결과와 범위가 명확해진 뒤 이 문서를 읽는다.

## 수직 단위로 구현한다

타입 전체, 상태 전체, UI 전체를 차례로 완성하기보다 필요한 계층을 관통해 하나의 검증 가능한 동작을 만드는 단위를 우선한다.

예:

- 변경 동작을 추가하기 전에 기존 데이터를 먼저 화면에 표시한다.
- 보조 동작보다 폼의 핵심 제출 흐름 하나를 먼저 완성한다.
- 라우팅 패턴을 전체에 적용하기 전에 호환 가능한 라우트 하나를 이전한다.

가능하면 각 단위 사이에도 애플리케이션을 실행할 수 있게 유지한다.

## 기존 경계를 따른다

- 적합한 기존 컴포넌트, 디자인 토큰, 상태 패턴, 요청 클라이언트를 재사용한다.
- 도메인 결정을 표현 전용 컴포넌트에 넣지 않는다.
- 브라우저 전용 API는 적절한 클라이언트 경계 안에서 사용한다.
- 승인된 설계가 바꾸지 않는 한 공개 컴포넌트 props를 유지한다.
- 아직 존재하지 않는 두 번째 사용처를 위해 추상화를 만들지 않는다.

## 상태를 의도적으로 모델링한다

불가능하거나 충돌하는 상태는 표현하기 어렵게 만든다. 서로 다른 UI나 허용 행동을 만드는 상태는 구분한다. 중복 비동기 작업이 문제를 만들면 이를 막고, 관련이 있다면 오래된 응답과 취소를 어떻게 처리할지 정한다.

편집, 낙관적 업데이트 또는 동기화 필요가 없다면 서버 데이터를 로컬 상태에 복사하지 않는다.

## 사용자 변경을 보존한다

수정 전에 작업 트리를 확인한다. 관련 없는 변경을 버리거나 덮어쓰거나 재포맷하지 않는다. 생성 파일이 바뀌면 결과가 결정적이고 요청한 작업에 포함되는지 확인한 뒤 반영한다.

## 위험이 커지면 알린다

구현 중 다음 사실을 발견하면 멈추고 사용자에게 알린다.

- 예상보다 많은 소비자가 영향을 받는다.
- 데이터 계약 또는 마이그레이션이 필요하다.
- 새 의존성이나 외부 서비스가 필요하다.
- 접근성 또는 브라우저 호환성 트레이드오프가 생긴다.
- 변경을 독립적으로 롤백할 수 없다.
- 커밋하지 않은 사용자 변경과 충돌한다.

근거, 영향, 가장 작은 합리적인 선택지를 설명한다. 작업 범위를 조용히 넓히지 않는다.
