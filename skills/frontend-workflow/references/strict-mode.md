# 엄격 모드

사용자가 `strict`를 명시했거나 고위험 변경에 대한 자동 추천을 승인했을 때 이 문서를 읽는다.

엄격 모드의 목적은 문서를 늘리는 것이 아니라 수용 기준이 구현과 검증까지 끊기지 않고 연결되게 하는 것이다.

## 시작 조건

엄격 모드는 다음 두 경우에만 활성화한다.

- 사용자가 `$frontend-workflow strict ...`처럼 명시적으로 요청했다.
- Codex가 고위험 조건을 발견해 추가 비용과 산출물을 설명했고 사용자가 승인했다.

사용자가 거절하면 일반 고위험 절차로 돌아간다. 이미 명확한 승인에 반복해서 확인을 요구하지 않는다.

## 작업 디렉터리

저장소 관례가 없다면 다음 위치를 사용한다.

```text
docs/frontend-workflow/<feature-slug>/
├── spec.md
├── plan.md
├── journal.md
└── trace.yaml
```

`<feature-slug>`는 짧은 영문 kebab-case로 정한다. 저장소에 기존 설계 문서 위치가 있으면 해당 관례를 우선하고 네 파일의 상대적인 역할만 유지한다.

초기 파일은 `assets/templates/`의 템플릿을 복사해 작성한다. 사용하지 않는 예시와 안내 문구는 제거한다.

## 1. 명세

`spec.md`에 다음을 작성한다.

- 사용자 시나리오
- `AC-001` 형식의 관찰 가능한 수용 기준
- 관련 UI 상태
- 제외 범위

ID는 기능 디렉터리 안에서 유일해야 한다. 내부 구현 방식은 수용 기준에 넣지 않는다. 사용자에게 명세 승인을 받은 뒤 구현 계획으로 이동한다.

## 2. 계획

`plan.md`에서 각 작업을 하나 이상의 수용 기준과 연결한다. 각 작업에는 검증 방법을 적는다. 구현 순서는 사용자가 확인할 수 있는 작은 수직 단위가 되게 한다.

새 의존성, 공개 인터페이스 변경, 데이터 이전 또는 롤백 제약이 있으면 계획 승인 전에 명시한다.

## 3. 추적

`trace.yaml`에는 모든 수용 기준의 상태와 근거를 기록한다.

- `pending`: 아직 구현 또는 검증되지 않았다.
- `verified`: 구현이 있고 테스트 또는 수동 검증 근거가 있다.
- `excluded`: 합의에 따라 제외했으며 이유가 있다.

검증하지 않은 항목을 `verified`로 표시하지 않는다. 파일 경로는 저장소 루트 기준 상대 경로로 적는다.

## 4. 구현과 일지

일반 구현 지침을 따르되 수직 단위가 끝날 때마다 `journal.md`에 중요한 관찰, 결정, 버린 대안, 검증 결과를 추가한다. 단순 명령 실행이나 자명한 수정은 기록하지 않는다.

구현 중 수용 기준의 의미나 범위가 바뀌면 코드만 맞추지 말고 명세와 계획을 먼저 갱신해 사용자에게 알린다.

## 5. 검사와 리뷰

저장소 루트에서 다음 명령을 실행한다.

```text
python3 <skill-path>/scripts/check_trace.py docs/frontend-workflow/<feature-slug>/trace.yaml --root .
```

검사는 ID, 상태, 근거, 파일 존재 여부를 확인한다. 테스트 내용의 정확성이나 구현 품질을 증명하지는 않는다.

검사가 통과한 뒤 일반 검증과 최종 리뷰를 수행한다. 완료 보고에는 수용 기준별 상태, 자동 검사 결과, 수동 검증, 남은 위험을 포함한다.
