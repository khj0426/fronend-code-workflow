# 검증

변경의 실패 가능성과 저장소가 이미 제공하는 기능에 맞춰 검사를 선택한다. 검사 수가 많다고 항상 더 좋은 것은 아니다.

## 기본 검사

가장 집중된 검사부터 실행하고, 위험이 정당화하면 더 넓은 검사를 수행한다.

- 수정한 파일의 포맷 또는 린트
- 타입 검사
- 관련 테스트
- 번들링, 라우팅, 렌더링 또는 프레임워크 동작이 바뀔 수 있으면 프로덕션 빌드

최종 종료 상태를 확인한다. 기존의 관련 없는 실패와 이번 변경으로 생긴 실패를 구분한다.

## 동작에 맞는 근거를 선택한다

| 변경 | 유용한 근거 |
| --- | --- |
| 순수 변환 또는 상태 리듀서 | 경계 사례를 포함한 단위 테스트 |
| 폼 또는 상호작용 컴포넌트 | 컴포넌트 상호작용 테스트와 키보드 확인 |
| 내비게이션 또는 여러 페이지 흐름 | 브라우저 또는 E2E 흐름 |
| 공용 컴포넌트 또는 디자인 토큰 | 소비자 검사와 시각적 비교 |
| 비동기 변경 작업 | 처리 중, 성공, 오류, 재시도, 중복 동작 확인 |
| SSR 또는 하이드레이션 경계 | 프로덕션 빌드와 브라우저 콘솔 확인 |
| 반응형 레이아웃 | 좁은 화면과 넓은 화면 확인 |
| 테마에 따른 UI | 라이트 모드와 다크 모드 확인 |

작은 변경을 증명하기 위해 새 테스트 프레임워크를 설치하지 않는다. 자동화가 없으면 집중된 수동 검사를 수행하고 수동 검사라고 보고한다.

## 브라우저 검증

화면에 보이거나 상호작용하는 변경은 브라우저를 사용할 수 있을 때 렌더링 결과를 확인한다. 변경과 관련 있는 항목만 검증한다.

- 주요 상호작용과 복구 흐름
- 영향을 받는 화면 너비의 레이아웃
- 포커스 순서와 보이는 포커스
- 접근 가능한 이름, 역할, 상태, 오류 연결
- 변경한 테마와 모션 설정
- 변경으로 생긴 콘솔 및 네트워크 오류

빌드 성공은 UI 사용성을 증명하지 않는다. 스크린샷은 상호작용 동작을 증명하지 않는다. 주장에 맞는 근거를 사용한다.

## 검증 공백을 보고한다

인증 정보, 데이터, 브라우저, 외부 서비스 또는 사용할 수 없는 명령 때문에 검사가 막히면 다음을 밝힌다.

1. 검증하지 못한 항목
2. 수행할 수 없었던 이유
3. 대신 수행한 검사
4. 남은 위험

## 최종 diff를 리뷰한다

변경과 관련 있는 항목만 확인한다.

- 로딩, 오류, 빈 상태, 복구 흐름의 누락
- 키보드 조작, 포커스, 이름과 상태 알림의 회귀
- 좁은 화면, 긴 콘텐츠, 테마 차이
- 중복 요청, 오래된 상태, 정리 작업과 경쟁 상태
- 서버와 클라이언트 경계 및 브라우저 전용 API

실제로 완료된 검사만 결과로 보고한다.
