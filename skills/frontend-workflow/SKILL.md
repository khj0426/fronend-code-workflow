# 프론트엔드 워크플로

구현 방법에 대한 추측이 아니라 사용자가 관찰할 수 있는 결과에서 출발한다.

## 맥락부터 확인한다

제안하거나 수정하기 전에 다음을 수행한다.

1. 저장소 지침을 읽고 작업 트리를 확인한다.
2. 기존 UI 흐름, 테스트, 사용 중인 패턴을 찾는다.
3. 최근 변경이 현재 동작을 설명할 수 있으면 이력을 확인한다.
4. 관련 없는 변경과 사용자가 작성한 변경을 보존한다.

저장소의 기존 도구와 관례를 우선한다. 국소적인 변경을 위해 의존성, 외부 서비스, 테스트 프레임워크 또는 광범위한 리팩터링을 추가하지 않는다.

## 작업 강도를 조절한다

실제 영향 범위에 따라 변경을 분류한다. 새로운 정보로 위험이 커지면 더 강한 절차로 올리고 사용자에게 알린다.

사용자가 프롬프트에 `strict`를 명시하면 [references/strict-mode.md](references/strict-mode.md)를 읽고 엄격 모드를 적용한다. 고위험 변경이지만 사용자가 엄격 모드를 요청하지 않았다면 엄격 모드가 필요한 이유와 추가되는 산출물을 한두 문장으로 설명하고 적용 여부를 묻는다. 승인 전에는 문서나 추적 파일을 만들지 않는다.

### 작은 변경

인터페이스나 상태 전이를 바꾸지 않는 문구, 스타일, 정적 콘텐츠 변경에 사용한다.

- 눈에 보이는 결과를 한 문장으로 확인한다.
- 관련 소스와 기존 패턴을 확인한다.
- 요청을 만족하는 가장 작은 일관된 변경을 적용한다.
- 집중된 코드 검사를 실행하고 가능하면 영향을 받은 UI를 확인한다.
- 별도의 계획 문서를 만들지 않는다.

### 일반 기능

사용자 입력, 로컬 또는 원격 상태, 내비게이션, 비동기 동작, 여러 UI 상태가 포함된 변경에 사용한다.

1. [references/specification.md](references/specification.md)를 읽는다.
2. 사용자 시나리오, 관련 상태, 수용 기준, 제외 범위를 제안한다.
3. 요청에 선택 사항이 이미 명확하지 않다면 구현 전에 승인을 받는다.
4. [references/implementation.md](references/implementation.md)를 읽고 작은 수직 단위로 구현한다.
5. [references/verification.md](references/verification.md)를 읽고 저장소에 이미 있는 도구로 검증한다.
6. 완료를 보고하기 전에 [references/review.md](references/review.md)를 읽는다.

### 고위험 변경

공용 UI 요소, 디자인 시스템, 인증, 라우팅, 공개 컴포넌트 API, 데이터 계약, 프레임워크 이전 또는 소비자가 많은 변경에 사용한다.

- 일반 기능 절차를 모두 따른다.
- 영향을 받는 소비자, 롤백 조건, 호환성 요구사항을 확인한다.
- 합리적인 대안을 비교하고 설계 승인을 받는다.
- 독립적으로 검증할 수 있는 단계로 나누고 단계마다 회귀를 확인한다.
- 저장소 관례나 작업 위험이 영구 기록을 정당화할 때만 설계 또는 결정 문서를 만든다.

다음 조건 중 하나가 핵심 범위에 포함되면 엄격 모드를 자동으로 추천한다.

- 인증, 권한, 결제 또는 개인정보 처리
- 여러 화면에 영향을 주는 라우팅이나 데이터 계약 변경
- 공용 컴포넌트 API 또는 디자인 시스템 변경
- 단계적 이전, 호환성 유지 또는 명시적인 롤백이 필요한 작업
- 실패 비용이 크거나 요구사항과 검증의 추적이 필요한 작업

추천은 승인이 아니다. 사용자가 거절하면 일반 고위험 절차로 진행한다.

## 권한의 경계를 지킨다

구현 승인은 요청한 결과에 필요한 변경만 허용한다. 커밋, 푸시, PR, 배포, 외부 메시지, 새 서비스, 파괴적 작업은 사용자의 명시적 승인이 필요하다.

명령이나 UI 확인을 수행할 수 없으면 가장 안전한 관련 대체 검증을 실행하고 한계를 밝힌다. 실행하지 않은 검사를 통과했다고 표현하지 않는다.

## 근거와 함께 마무리한다

다음 내용을 보고한다.

- 사용자 관점에서 달라진 점
- 변경한 주요 파일이나 영역
- 수행한 검사와 결과
- 검증하지 못한 동작, 받아들인 한계 또는 유용한 다음 작업

보고의 길이는 변경 규모에 맞춘다. 선택적인 후속 아이디어를 완료한 범위처럼 표현하지 않는다.
